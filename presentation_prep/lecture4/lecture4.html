A span may represent an LLM call, retrieval or a tool invocation. The trace is the execution record, not a transcript alone. OpenTelemetry provides a common tracing model. Integration and payload details still matter when sending data to another backend.

TRACES AND SPANS

What a trace helps us investigate

01

Slow response

Which span dominates the request? Is the agent making repeated tool calls?

02

Poor answer

What did retrieval return? What did the model receive? Did memory load the expected history?

03

Unexpected cost

How many model calls ran? Where available, compare token usage by span and version.

Execution succeeded. That alone does not tell us whether the answer was useful.

Span durations can overlap, so summing child durations is not always equal to request latency. Token and cost data depend on instrumentation and model support. Separate evidence from hypotheses during debugging.

GUIDELINES

A conditional rule

Only apply the expectation when the user describes failed attempts.

The judge needs the relevant conversation context.

JUDGE_MODEL is the configured judge endpoint. A guideline cannot evaluate hidden conversation history that it never receives. Avoid applying this criterion to standalone questions without its conditional wording.

https://mlflow.org/docs/latest/genai/eval-monitor/scorers/llm-judge/guidelines

from mlflow.genai.judges import make_judge

context_judge = make_judge(

PRODUCTION OBSERVABILITY

Tiered evaluation in production

Cheap checks run broadly. Expensive evaluations run on a sample.

Tier 1: code-based checks

Coverage: every request

  • Latency, token counts and cost
  • Tool usage and error rates
  • Format validation and rule violations
  • Length checks and regex matching

Example: process new traces every 15 minutes.

Tier 2: LLM-based scorers

Coverage: sampled requests

  • Relevance and correctness
  • Tone and professionalism
  • Random or stratified sampling
  • Additional coverage of edge cases

Example: evaluate a 5–10% sample hourly.

Illustrative rates and schedules. Run code checks in application code or jobs; MLflow automatic evaluation supports LLM judges.

Evaluate broadly with code. Use LLM scorers where context matters.

The rates and cadence are illustrative. Cheap checks may run in application code or a scheduled job. Current MLflow automatic evaluation supports LLM judges, while custom code-based scorers are for offline evaluation. See https://mlflow.org/docs/latest/genai/eval-monitor/scorers/custom/
